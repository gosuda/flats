# Lifecycle transport and operator decisions

## Operator authority contract

HTTP reachability, agent API access, `ViaConsole`, Tailscale identity, and
`X-Flats-Console`/Origin/Sec-Fetch-Site headers confer no decision authority.
Browser headers remain CSRF defenses. An `api.OperatorAuthority` supplied on
`api.Server.Operator` independently validates operator sessions. Nil authority
fails closed, including approval/rejection and all console mutations.

The embedding application constructs one authority with
`api.NewOperatorAuthority(credential)` and wires its `ValidateDecision` method
as `core.Config.ValidateOperatorDecision`. Use the same instance in the core
callback and every management API server. Core must independently validate the
private context proof for decisions and nonlocal provider permission mutations.
Session authentication establishes identity/authority only; publish and each
visibility change still require separate explicit candidate confirmation.

Bootstrap uses an independently provisioned, high-entropy operator credential
(at least 32 bytes; recommended: 32 random bytes encoded as base64url). Provision
it through an operator-controlled channel inaccessible to the agent. The app
owner provides hidden startup input and console credential entry. Do not put
it in process arguments, agent-readable settings/data directories, source trees,
HTTP GET replies, logs, pending approval URLs, MCP tools, or CLI commands.
Directory-upload MCP tools can read caller-selected host directories: file mode
0600 is insufficient separation from an agent with the same OS identity. Keep
the operator credential out of those directories and restrict host filesystem,
process-memory and browser access when running an untrusted agent.

This is a concrete credential/capability boundary, not a claim that HTTP can
distinguish a human from a process holding the human's credential. An agent with
operator-secret, authenticated browser-cookie, server/browser-memory, or OS
administrator access is outside the boundary. Deployment isolation must enforce
those assumptions. Private visitor access continues to use existing loopback
and tailnet ACL policy; this adds no visitor accounts or login requirement.

## Console session handshake

`POST /console/api/operator/session` accepts JSON `{"credential":"..."}` with
the usual console CSRF headers. Credentials are accepted only over TLS or a
loopback connection. Valid credentials issue a random 256-bit session cookie,
`flats_operator`, scoped to `/console/api`, HttpOnly and SameSite=Strict (Secure
on TLS). JSON reports only `{"status":"operator_authorized"}`. Console fetches
must send same-origin cookies. Neither a GET nor an API/MCP/CLI operation issues
operator authority. Agent client headers remain forbidden on console routes.

`DELETE /console/api/operator/session` requires a valid session and console
CSRF headers, revokes it immediately and clears its cookie. Sessions expire
after eight hours, and at most 64 live sessions are retained. The server stores
credential/session hashes only. A new authority, including server restart,
invalidates all sessions; re-enter the externally provisioned credential.
Credential rotation means constructing a new authority with the replacement
credential and updating both API and core binding. No credential is persisted
or generated by the API.

Failures return 403 with exact `category`: `operator_unavailable` (not
configured), `operator_required` (missing/expired session),
`invalid_operator_credential` (bad bootstrap credential), or
`operator_secure_transport_required` (nonlocal plaintext bootstrap). No failure
includes the submitted credential or cookie.

## Ownership and verification

Transport owns `internal/api`, `internal/mcpx`, `internal/cli` and this document.
App configuration, console UI, providers and acceptance gate are integration
owned; core/store/bundle are core owned. The prerequisite network contract was
adopted only from the exact coordinator-granted commit. Full lifecycle binding
and integrated validation remain pending until exact core exports are granted.

Disposable tests cover forged console headers against approve/reject/settings/
delete, invalid credentials/no GET bootstrap, legitimate operator context proof,
authority instance binding, logout, expiration/restart, and CSRF/client rejection.
CLI tests cover pending exit 3 and approval links for upload/deploy/rollback/both
visibility directions, plus read-only approvals and absent decision commands.
These tests do not prove live internet exposure or visitor ACL behavior.
