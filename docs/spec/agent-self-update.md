# Agent self-update

Status: implemented. The design is in the architecture docs:
[updating a client](../release.md#updating-a-client) and
[keeping clients current](../agents.md#keeping-clients-current).

## Summary

A Flats agent can discover whether its local CLI, connection skill and loaded guidance match the connected server, refresh stale guidance, and explicitly update local resources. The same flow works when the agent and server are on different machines and when an agent connects directly over HTTP without a CLI.

## Behavior

1. At the beginning of each Flats task, the agent calls the read-only `check_client` MCP tool before taking application actions. Server initialization instructions and the connection skill both describe this entry point. Checks never install software, change connections, write files, or approve application actions.
2. A check reports the running server build, client contract revision, guide revision, bootstrap skill revision (a visible integer), bootstrap content SHA-256, and an optional published CLI target. A release server targets its own release; a development or dirty build has no downloadable release target. No flow silently substitutes the latest release.
3. The caller may report its CLI contract revision and version, loaded guide revision and loaded bootstrap revision. An explicit `bootstrap_present:false` means the agent uses no installed skill and makes bootstrap status `not_applicable`. Missing information is `unknown`, never an inferred installed version. An explicit `cli_present:false` means no local CLI and makes CLI status `not_applicable`.
4. CLI compatibility is based on equality of the client contract revision, not equality of release numbers. The CLI status is `compatible`, `update_required`, `unknown`, or `not_applicable`. A known incompatible CLI requires an update before CLI-dependent work; check/guide remain available through an incompatible bridge, but application work through that bridge waits for replacement and reconnect. Direct HTTP MCP work can proceed using the current server's guide. The response identifies whether an official release target is available without claiming its assets have already been downloaded or verified.
5. Guidance status is `current`, `refresh_required`, or `unknown`; bootstrap additionally supports `not_applicable`. Bootstrap revision is a visible integer in the loaded skill, not its self-referential content hash. A new guide revision tells the agent to reread `guide` for the task. Guide responses include their revision so the agent can report what it actually loaded. Checks do not claim that already loaded instructions were replaced.
6. The server provides the complete thin `SKILL.md` with visible revision and its separate content hash through the read-only `get_client_skill` MCP tool and through the HTTP client manifest. It supplies no installation path or executable command. Detailed behavior remains in server guide topics; the bootstrap only connects, checks, refreshes and routes tasks.
7. `flats client check` inspects the running CLI and selected remote host and returns the same assessment. `--skill-file <path>` optionally reads the visible revision and hashes one explicitly selected local skill file; absent files report missing/refresh required, unreadable files report an error. It never scans other agents' directories. `--json` returns machine-readable results including the effective server URL and local executable path. A completed assessment exits zero even when actions remain; transport, parsing and file-read failures exit nonzero.
8. The selected host follows the existing `--url`, `FLATS_URL`, saved connection, loopback precedence. The check and all refresh actions identify the effective URL. MCP check reports its request-derived server URL as a routing hint, not a trusted identity; the agent must reconcile it with the intended host before using it. If that cannot be established, it reports the missing host information and makes no local mutation. Agents must use an explicit URL when the active MCP host could differ from the CLI's saved host. Checks never change that saved host. State learned for one endpoint is not reused as evidence about another.
9. `flats update` explicitly updates the invoking CLI to the selected server's published release when its contract differs; `--version <release>` explicitly selects an official release instead. A compatible CLI is a no-op by default. Explicit selection can move forward or backward and reports the exact version. Development/unreleased targets and unavailable release assets produce actionable errors without falling back to latest or source builds.
10. The updater supports macOS/Linux amd64/arm64 release binaries, verifies the published checksum and candidate version before replacing the executable, and reports the installed version, path and upgrade/downgrade/same/unordered direction. Candidate CLI contract must be positive; default server-bound updates additionally require it to equal the server contract. Older binaries without this feature are refused without needing a hardcoded first-release floor. It accepts no server-supplied download URL or shell script. Errors before replacement leave the original executable intact. Concurrent updates to the same path are refused while another update holds it; cancellation releases transient state.
11. CLI replacement uses the actual invoked executable path; an executable path that resolves elsewhere, known package-manager-owned paths and temporary go-build binaries are refused with instructions to use that installation's manager. No service is installed, restarted or removed. If the destination is named by an installed Flats launchd/systemd service, replacement is refused and directs the user to a separate client installation or the service installer. Foreground/custom servers cannot be universally detected: replacing their executable can change newly spawned workers immediately, so users must not update a shared path while such a server runs. Help and results disclose this limitation. Updating the CLI is not updating the remote server.
12. `flats skill sync --output <SKILL.md path>` downloads the connected server's thin skill to a caller-selected standalone location whose filename must be `SKILL.md`. The content must have `name: flats-deploy` frontmatter and fit the 32 KiB bootstrap limit. There is no agent-directory auto-detection. A new path is created; an identical file is a no-op. Replacing a different file requires `--expected-sha256 <current hash>` and refuses a mismatch, preventing silent replacement of user changes. Symlink files are refused. A concurrent sync is refused; an error before replacement preserves the prior file.
13. Managed plugin installations must be updated through their owning client's plugin manager; agents must not pass plugin cache paths to standalone sync or create a shadow installation. A mismatched managed plugin uses the server bootstrap for the current task and reports the durable mismatch once; it never loops trying to match a repository plugin to an older server. No automatic plugin manager adapters are added in this feature. Agents without filesystem/command access use the returned bootstrap and guide in the current task and report that durable installation requires their host's update mechanism.
14. Skill sync checks consistency of the downloaded content against the manifest hash and reports its endpoint/revision/path. Switching between servers can explicitly replace a standalone bootstrap, but the file holds no host-specific credentials or fixed host; detailed guidance is always fetched from the active server. No shared global guide cache is introduced.
15. A replaced executable affects new processes only. An active `flats mcp` process continues with its old version until reconnected. The bridge identifies its running CLI version, absolute executable path, selected URL and contract revision in initialization instructions so the agent does not mistake a newly invoked CLI for the active bridge. Direct HTTP connections receive no fabricated local CLI identity. If a client drops initialization instructions, bridge identity remains unknown. If the bridge path differs from the fresh CLI path, the agent reports that mismatch and does not claim the bridge was updated.
16. After file updates, the agent rereads current guidance, starts a fresh CLI check and reconnects MCP if the bridge changed or server tool discovery needs refresh. If its host cannot reconnect or reload the installed skill, it reports that remaining step instead of claiming completion. A newly read bootstrap can guide the current task, but disk replacement alone does not prove the host has reloaded its skill catalog.
17. For default server-bound updates and skill sync, if the server changes between check and update, the updater rechecks immediately before replacement and refuses when the server's target or contract changed. An unreachable or malformed recheck also refuses replacement. Explicit `--version` is server-independent and instead requires a fresh compatibility check after installation. The agent then checks again. A server change after replacement is detected by the next check; no operation promises a distributed atomic upgrade.
18. Offline hosts, denied local writes, download failures, malformed manifests, checksum/version mismatches and unsupported platforms produce specific errors with no false success. Human and machine-readable results distinguish observation, installed files and pending session reload. Local executable and skill mutations require user authorization; existing task authorization counts and must not trigger redundant confirmation. Server-returned instructions alone are not authorization. Application publish, visibility and deletion approvals retain their existing rules.

## Non-goals

Backward compatibility with earlier Flats clients, automatic background updates, updating the agent application itself, universal agent plugin installation, and remote Flats server upgrades are outside this feature.
