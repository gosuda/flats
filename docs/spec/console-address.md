# Console listener address

Status: implemented.

## Summary

Rename the operator configuration key `host.management_addr` to
`host.console_addr`. The listener serves the console, HTTP API, MCP and other
management routes together, so the new name does not make it console-only.
This is a configuration rename with an automatic schema migration; it does
not move or expose a listener.

## Behavior

1. `host.console_addr` is the canonical configuration key. It keeps the
   existing address validation, default `127.0.0.1:7878`, restart requirement
   and single-run override behavior. `host.local_addr` remains unchanged,
   including existing listener-address collision checks and their ephemeral
   port exception.
2. The configuration schema advances from 4 to 5 because a key is renamed.
   The 4-to-5 migration moves an explicitly present `host.management_addr`
   value to `host.console_addr` without changing its value, and removes the
   old key. The normal address validation still rejects invalid types or
   addresses after migration. If neither key is present, the migration
   leaves both absent; sparse files continue using `127.0.0.1:7878` without
   writing a default. An already present new key is retained when the old
   key is absent.
3. A file containing both keys is rejected, including when their values
   match. For schema 1–4 migration conflicts, the error names both keys;
   migration must not choose a winner. Schema 5 rejects the old key as
   unknown, whether alone or alongside `host.console_addr`, through its
   existing unknown-key validation. Rejection leaves the file and
   configuration history untouched.
   Older schemas accept the old key through their ordered migration chain,
   including the new 4-to-5 step. Existing migration backup, validation and
   atomic persistence rules apply. Successful persistence keeps the original
   schema 4 file in configuration history. An older binary refuses schema 5
   without changing it; returning to an older binary requires restoring a
   compatible historical configuration and its corresponding data backup.
   This step needs no confirmation because it preserves network and
   credential authority.
4. Offline configuration commands, key discovery, validation messages and
   current examples use the new name. The old name is not a current-schema
   alias for `get`, `set` or `unset`; file migration is the compatibility
   path. Configuration-key maps, source metadata, validation error paths
   and runtime override keys use the new name; old-name overrides are
   rejected. Historical schema 1–4 fixture inputs keep their original names
   and defaults. Their migration-to-current expected outputs use schema 5 and
   the new key; they are not frozen historical inputs.
5. Bind addresses, listener ports, accepted Host and Origin rules, route
   availability, local-only permissions and embedded Tailscale/NetBird
   console behavior are unchanged. A non-loopback bind stays non-loopback;
   an omitted address stays loopback. HTTP API and MCP continue to use the
   same listener as the console. No network exposure is widened.
6. Existing CLI and installer flags keep their names and behavior,
   including `--listen`, `--console` and `--console-host` where supported.
   This change does not rename commands, flags, HTTP routes, environment
   variables, flat addresses or client connection fields. Saved configuration
   generated by those paths uses the canonical new key.
7. The SettingsConfig view reports `schema_version: 5` and
   `host.console_addr`, matching the configuration key. It removes the old
   `host.management_addr` JSON field. Existing console consumers follow the
   new field and use the label "Console address", without a layout change.
   HTTP route names remain unchanged.
8. During upgrades the installer's informational console-URL reader
   recognizes both the new key and the legacy key, so it can find the same
   address before the host migrates the file. It prefers the new key when
   both appear, regardless of their object order or whether the JSON is
   compact or multiline. It falls back to the legacy key only when the new
   key is absent. This does not validate the configuration or make a
   conflicting file acceptable. The host's canonical migration and
   validation still reject both-key files before serving.
